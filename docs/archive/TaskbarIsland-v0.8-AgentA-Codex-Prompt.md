## 4. Phase A2 — Phone Link spike (go / no-go BEFORE building the UI)
Windows has no public call-control API for Phone Link. Reading calls is feasible; controlling them is the risk. Prove it on this machine with a real phone linked. Deliver `docs/spikes/phone-link.md` with facts, logs (masked) and a decision for each item. Prototype in `spikes/phone-link/` (a throwaway crate, not shipped).

**(a) Detect an incoming call.** Try in this order and record which works, how reliably, and with what permissions:
1. `UserNotificationListener` (Windows.UI.Notifications.Management). Needs package identity (MSIX or a sparse package) and user consent (`RequestAccessAsync`). Check how the app is packaged today and what adding a sparse package would cost.
2. UI Automation: watch the toast / Action Center (ShellExperienceHost) and the Phone Link window for call elements.
3. The notification store `%LOCALAPPDATA%\Microsoft\Windows\Notifications\wpndatabase.db` (undocumented SQLite + WAL; read-only, shared access, copy-then-read if needed). Phone Link's AUMID is `Microsoft.YourPhone_8wekyb3d8bbwe!App`.
Log the real toast XML of an incoming call, a missed call, an ended call and an in-progress call (mask numbers). Find how the caller name and number appear and which language variants exist; match on structure (scenario/buttons/AUMID), never on English words alone.

**(b) Hide Phone Link's popup but keep the information.** Hypothesis: turn off *Show notification banners* for Phone Link while leaving *Show notifications in notification center* on; the toast then never pops up, yet the notification is still delivered to the notification store/listener. Verify with the real app. Find where Windows stores this (registry under `HKCU\Software\Microsoft\Windows\CurrentVersion\Notifications\Settings\<AUMID>`; check the actual value names such as `ShowBanner`, `ShowInActionCenter`, `Enabled`). Setting it requires the user's consent through the setup card (CallSetup artboard); never change it silently, always offer to restore it (Settings → "Show Phone Link popups again" in the tray menu). Also handle the case where the user changes it back.

**(c) Answer / Decline / End.** Investigate, in this order: UI Automation `InvokePattern` on the toast buttons or on Phone Link's call window (find stable `AutomationId`s, not names); do it without stealing focus and while Phone Link is minimized if possible. Record whether it works when the screen is locked, when Phone Link is closed (it should be running in the background; check how it behaves), and after a Phone Link update. If actions cannot be invoked reliably, the fallback is: the pill and card show the call, and the primary action becomes "open Phone Link" (bring its call window to the front). State this clearly in the doc.

**(d) Audio.** Prove with code: enumerate render endpoints (`IMMDeviceEnumerator`), find the current default *communications* and *console* endpoints, label them (friendly name, form factor, Bluetooth via `PKEY_Device_EnumeratorName` containing `BTHENUM`/`BTHHFENUM`, "Hands-Free" vs "Stereo" profile), switch the default (`IPolicyConfig`, an undocumented but widely used COM interface; wrap it in one module with a runtime capability check and a clear failure result), read and set endpoint volume (`IAudioEndpointVolume`), pair the microphone of the same physical device through `PKEY_Device_ContainerId`, and react to device changes with `IMMNotificationClient` (no polling). Find out which role (communications vs console) Phone Link's audio actually follows and write it down. Decide whether to restore the previous default device when the call ends (recommended: yes, with a setting).
**(e) "Phone" output tile** (hear the call on the phone): only keep it if (c) proves Phone Link's toggle can be driven; otherwise hide that tile.

Stop after the spike and report in `coordination/from-A.md` with a plain GO / PARTIAL / NO-GO for detect, hide-popup, actions, audio. Continue with the parts that are GO or PARTIAL; do not fake the rest.

## 5. Phase A3 — Call activity
Build from the Call artboards. Use real data only; no mock caller in release builds (a debug-only simulator that fires fake call events is welcome, used by tests and by you to exercise the UI without a phone).
- **State machine** (pure, unit-tested): `Idle → Ringing → Active → Ended`, plus `Missed`. Inputs: call events from the provider; user actions; device changes. Provider trait `CallProvider` with `PhoneLinkProvider` and `SimulatedProvider` so the logic is testable without Windows.
- **Pill:** Ringing = avatar (initials, color from a hash of the name), ringing badge, name, Decline, Answer (CallPillIncoming). Active = green phone glyph, name, mm:ss timer, End (CallPillActive). Ended shows a check for 2 s; Missed shows a missed-call glyph for 4 s. Buttons are 34 × 34 and keyboard reachable (Tab, Enter; Esc dismisses the ringing pill without declining).
- **Card:** CallIncoming (Answer/Decline 60 DIP high, name, masked number, ring output hint), CallActive (name, number, timer, five output tiles, current-output line, microphone note, volume slider, End), CallDeviceTip, CallSetup (first run), CallIdle (phone status + output tiles). The output tiles come from the real device list; only show tiles that exist (always Speakers; the others only when present). The active tile reflects the real default and updates live. Clicking a tile switches output (and the paired microphone), shows a green ring on success, or an amber glyph with "Windows blocked the change" and an "Open sound settings" link (`ms-settings:sound`) on failure.
- **First run (CallSetup):** (1) notification access, (2) hide Phone Link popups, (3) Phone Link connected check. Each row shows a green check when satisfied. The rail icon is always visible; the Call card shows CallSetup until every row is satisfied.
- Phone Link not installed / not signed in / phone not connected: CallIdle shows a muted state icon with a tooltip that says which; no sentences on the card.
- Caller identity: show the name as given; if only a number is given, show it formatted. Contacts are not read. Avatar = initials or a phone glyph.
- Ringtone: do not play any sound; Phone Link's own audio is untouched.
- Resource budget: idle CPU ≈ 0 (event-driven only), memory increase < 10 MB for the call module.
Tests: state-machine table tests (every transition, double events, answer after remote hang-up, end while ringing), provider contract tests with the simulator, audio module tests with a fake endpoint list, masking test for logs, pill priority tests, and layout tests for the pill (224 wide: nothing overflows with a 30-character name).
